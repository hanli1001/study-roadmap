0. 复现你的报错（外键开着 + 库里还有上回的 15 行）
======================================================================
库里现状：student_course = 15 行
   DROP TABLE IF EXISTS students -> IntegrityError -> FOREIGN KEY constraint failed

======================================================================
1. 关键区分：拦你的是「那 15 行」还是「外键声明」本身？
======================================================================
把 student_course 删空之后（外键声明还在）：
  foreign_key_list 仍然是： 2 条
  DROP TABLE students -> 成功了
  => 拦你的是「绳子表里指向学生的那些行」，不是那句 REFERENCES

SQLite 的规矩：DROP TABLE 若在外键开启时执行，会先做一次隐式 DELETE 把表删空；
这次隐式 DELETE 撞上了 student_course 里指向它的行 → IntegrityError。

======================================================================
2. 修法一：换 DROP 顺序 —— 先删绳子表，再删两张主表
======================================================================
   DROP TABLE IF EXISTS student_course -> 成功
   DROP TABLE IF EXISTS students -> 成功
   DROP TABLE IF EXISTS course -> 成功

======================================================================
3. 对照：外键关着的时候，你原来的顺序照样能过（所以这不是新 bug）
======================================================================
  PRAGMA foreign_keys = 0 （关着）
  原顺序三个 DROP 全部成功 —— 因为约束根本没在管事

=> 报错不是「加了外键把代码搞坏了」，而是「约束终于生效了，暴露出清理顺序本来就不对」。
   以前能过，只是因为外键一直是关的。

======================================================================
4. 为什么今天才撞到：空库时 DROP IF EXISTS 是空操作
======================================================================
  全新库（一张表都没有）+ 外键开着 → 三个 DROP 全过（IF EXISTS 直接跳过）
  ⇒ 只有「库里已经有上一次的数据」时才会撞。你之前几次跑，pragma 从没真生效过，所以没撞。
