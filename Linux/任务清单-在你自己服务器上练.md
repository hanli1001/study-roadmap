## ⚠️ 先看这个：危险命令清单（比学什么更重要）

**在真机上，下面这些一条敲错就可能回不来。练之前先把这张表记住。**

| 命令 | 危险在哪 | 安全替代 |
|------|----------|----------|
| `rm -rf /` 或 `rm -rf *` | **删库跑路**，且 Linux 没有回收站 | 先用 `ls` 看要删什么，再 `rm` 加具体路径 |
| `rm -rf $VAR/`（变量为空） | 变量没值时变成 `rm -rf /` | 用 `rm -rf "${VAR:?}"` —— `:?` 让空值直接报错 |
| `> 文件`（重定向到已存在的文件） | **直接清空原文件**，没有确认 | 先 `cp 文件 文件.bak` |
| `kill -9 <PID>` | 强杀，进程没机会存盘/关连接 | 先 `kill <PID>`（温和），等 5 秒再说 |
| `chmod -R 777 .` | 把整个目录开成谁都能改 | 只用 `chmod +x 某个脚本` |
| `docker rm -f $(docker ps -q)` | 删掉**所有**容器 | 先 `docker ps` 看清楚，再指定名字 |
| `apt install` 输错源 | 可能把依赖搞乱 | 不确定就别装 |

> 🔑 **一条铁律**：**不确定的命令，先在 `--help` 或空跑一遍。**
> 这跟你写代码前的「静态三查」是同一个习惯 —— 只不过这里查的是"这条命令会改什么"。

# 微课 1 · 找到东西（预计 20 分钟）

**这一课只有 3 个新概念**：① 路径（绝对 / 相对 / `~`）② 管道 `|` 与重定向 `>` ③ 看文件的三件工具分工

### 任务 1 · 先搞清楚"我在哪"

**目标**：登进服务器后，回答三个问题 —— 我在哪个目录？这个目录里有什么（**包括隐藏文件**）？我的家目录在哪？

**验证**：把你的答案和下面三条命令的输出对照
```bash
pwd            # 我在哪（print working directory）
ls -la         # 这个目录里有什么，-a 才会显示 . 开头的隐藏文件
echo ~ && cd ~ && pwd   # ~ 是家目录，cd 过去再看一次
```

**提示**：`ls` 不带 `-a` 时**看不到 `.env`、`.git` 这类文件** —— 而你的项目里恰恰有 `.env`。

<details><summary>答案</summary>

```bash
pwd                 # 实测：/home/ubuntu（你的用户名是 ubuntu，所以家目录不是 /root）
ls -la              # 会看到 . 和 .. 和隐藏文件（.bashrc / .git / .env 这类）
cd ~ && pwd         # 实测：/home/ubuntu —— ~ 展开成家目录
```
**概念**：`~` 是 shell 帮你展开的**家目录缩写**（谁的家？**当前登录用户的家**）；
`.` 是当前目录，`..` 是上一级。
</details>

### 任务 2 · 找到你的项目在哪

**目标**：不知道项目放哪了 —— 用命令把它找出来。

**验证**：找到后 `cd` 进去，`ls -la` 能看到 **`api.py` 和 `prescription_db.py`**，并且目录里有 **`.git`**。

> 🔴 **两条"看起来该有、其实没有"的坑（2026-10-05 实测，别拿它们当判据）**：
> - **`docker-compose.yml` 不在这个项目里** —— 它属于另一个项目（`~/openclaw-cn/`）。按它找会以为"我没这个文件"。
> - **这台机器没装 `locate`** —— 用它按名字查会直接报 `command not found`（想用得先 `sudo apt install mlocate`）。

**提示**：两个方向 —— 按**文件名**找，或按**内容**找。

> ⚠️ **按名字找会淹你一脸**：这台机器上叫 `api.py` 的文件有 **77 个**（几乎全是 Python 库自带的），**属于你的只有一行**。
> 翻不到底就换成"按内容找" —— 快、准，而且那是更该会的问法。

<details><summary>答案</summary>

```bash
# ① 按名字找 —— 实测刷出 77 条，你的在最后
find / -name "api.py" 2>/dev/null

# ② 只留你自己的：把系统目录筛掉（实测只剩 1 条）
find / -name "api.py" -not -path "/usr/*" -not -path "/snap/*" \
     -not -path "*/site-packages/*" -not -path "*/extensions/*" 2>/dev/null

# ③ 按内容找（推荐）：哪些 .py 里写了「方剂」—— 实测 2 条，两条都是你的
grep -rln "方剂" --include="*.py" /home/ubuntu 2>/dev/null

# ④ 找到之后进去看一眼
cd /home/ubuntu/study-roadmap && ls -la

# ⑤ 顺手确认"它活着"（这是任务 6–9 的正题，这里先尝一口）
curl -s -o /dev/null -w "%{http_code}\n" localhost:8009/docs
#   200  ← 服务在跑。也可以直接开浏览器看 http://123.58.220.17:8009/docs
```
**概念**：`find` 按名字/时间/大小找，`grep` 按内容找 —— **两个不同的问法，别混**。
**为什么推荐 ③**：`find` 问的是"**叫什么名字**"，`grep` 问的是"**里面写了什么**"。
你不记得文件叫什么，但记得它是干什么的 —— 那就该用 `grep`。

> ⚠️ **找到项目之后最常见的两个误判**（2026-10-05 学员真实踩到）：
> ① **`python api.py` 报"没有 fastapi"** ⇒ 不是项目坏了，是**依赖装在容器里、不在宿主上**（见上面〈补课 · Docker 是什么〉）
> ② **"我得先启动它"** ⇒ 它**已经在跑**（那个 200 就是证据）—— 你要学的是**怎么看它**，不是怎么点着它
</details>

### 任务 3 · 看文件，但别用 `cat`

**目标**：有个几百 MB 的日志文件，你要①看它有多少行 ②看最后 20 行 ③**实时**看新写入的行。

**验证**：三条都跑出来；第三条要能看到新内容**自己冒出来**（再开一个终端制造点流量）

**提示**：`cat` 会把整个文件吐到屏幕上 —— 大文件会把终端卡死。

<details><summary>答案</summary>

```bash
wc -l app.log          # ① 行数（word count -l = lines）
tail -20 app.log       # ② 最后 20 行
tail -f app.log        # ③ -f = follow，实时跟踪。Ctrl+C 退出
```
**概念**：看文件的三件工具分工 ——
`cat` 看小文件 ｜ `less` 翻大文件（`q` 退出）｜ `tail` 看末尾、`-f` 追新行。
**排查问题 90% 的时候你要的是 `tail -f`。**
</details>

### 任务 4 · 把命令的输出来回倒腾（管道）

**目标**：日志有 5 万行，你要**只看含 ERROR 的行，并且只数有多少条**。

**验证**：屏幕上只出现一个数字

**提示**：两条命令用 `|` 接起来 —— 前一条的输出，变成后一条的输入。

<details><summary>答案</summary>

```bash
grep ERROR app.log | wc -l          # 筛出 ERROR 行 → 数行数

# 变式：先筛再存，然后慢慢看
grep ERROR app.log > errors.txt
wc -l errors.txt
```
**概念**：`|`（管道）= **把左边命令的输出，接到右边命令的输入**。
这是 Linux 最值钱的一个符号 —— 小命令拼起来能干大事。
`>` 是**写入文件**（会覆盖！），`>>` 是**追加**。
</details>

### 任务 5 · 磁盘满了？先找出谁占地方

**目标**：服务器提示磁盘满，找出**占空间最大的 3 个目录**。

**验证**：输出 3 行，按大小从大到小排

**提示**：`du`（disk usage）算体积，`sort -rh` 按人类可读的大小**倒序**排。

<details><summary>答案</summary>

```bash
du -sh */ | sort -rh | head -3      # 当前目录下各子目录的体积，取前 3
df -h                                # 顺便看整个磁盘还剩多少
```
**概念**：`-h` = human readable（显示成 1.2G 而不是 1234567）；
`-r` = reverse（倒序），`sort -h` 才能正确比较 `9M` 和 `1.2G`。
**⚠️ `du -sh */` 只扫当前目录一层**，要往下钻就 `cd` 进最大的那个再跑一次。
</details>

## 补课 · Docker 是什么（10 分钟，用你自己的项目讲）

> 这一节不是额外的任务，是**补一个洞**。你服务器上的方剂 API 就是 Docker 跑的，
> 所以下面每一个数字都是**从你那台机器上实测出来的**。

### 要解决的是这个问题

你在本机写好了 `api.py`，怎么让它在你服务器上也能跑？传统办法是**到服务器上再装一遍**：
装 Python 3.12、装 fastapi、装 uvicorn、配环境变量……然后某天服务器上的 Python 升了个级，
你的程序就崩了 —— 这就是那句名言：**"在我机器上明明能跑"**。

**Docker 的办法：把"你的代码"和"它需要的整个运行环境"一起打包**，变成一张**安装盘**。
拿到哪台机器上，跑起来都跟在你本机一模一样。

### 只有三个词（就这三个）

| 词 | 是什么 | 生活里的类比 | 你的服务器上 |
|----|--------|-------------|-------------|
| **镜像**（image） | 打包好的"安装盘"：代码 + Python + 依赖，全在里面 | 一张**光盘** | `prescription-api:latest`（**245 MB**，2 个月前做的） |
| **容器**（container） | 从镜像**跑起来的一份**。同一张盘能跑很多份，互不干扰 | 光盘**放进光驱跑起来**的那一次 | `fangji-api`（正在跑） |
| **端口映射** | 容器里听的端口，要**接一根线**到宿主上，外面才够得着 | 包厢里的服务员，得**开个门**外面才叫得到 | 容器 `8000` → 宿主 **`8009`** |

### 现在回头看任务 6 那个"反直觉的结论"

```
宿主上：ss -tlnp  →  docker-proxy  (root)   听 8009     ← 只是"门"
容器里：uvicorn api:app --port 8000         听 8000     ← 真正干活的服务
```

**Docker 在你的服务前面站了一个"传话员"**：外面敲 8009，传话员转给容器里的 8000。
⇒ 所以你在宿主上**永远看不到 uvicorn 占着端口**，看到的是 `docker-proxy`。**这不是你查错了。**

### 你自己的 Dockerfile（15 行，全文）

这就是那张"安装盘"的**配方**。左边是命令，右边是人话：

```dockerfile
FROM python:3.12-slim        # ① 从哪开始：一个自带 Python 3.12 的迷你 Linux
WORKDIR /app                 # ② 进去之后站在 /app 这个目录
COPY requirements.txt .      # ③ 先把"要装什么"这份清单抄进去
RUN pip install --no-cache-dir -r requirements.txt   # ④ 照清单装依赖（这步最慢）
COPY . .                     # ⑤ 再把你所有代码抄进去
EXPOSE 8000                  # ⑥ 声明"我这个程序听 8000"（只是声明，不会真开端口）
CMD ["uvicorn", "api:app", "--host", "0.0.0.0", "--port", "8000"]   # ⑦ 跑起来之后执行这句
```

**①②③④ 是"准备环境"，⑤⑥⑦ 是"放代码 + 说怎么启动"。** 就这么点东西。

### 🔴 但这里有两个坑，你的项目正好都踩了

**坑 A：代码是"抄进去"的，不是"挂进去"的。**
第 ⑤ 行 `COPY . .` 在**做镜像的那一刻**把代码复制进镜像。之后你在
`/home/ubuntu/study-roadmap/` 里改了 `api.py`，**容器里跑的还是 7 月 31 日那份旧代码**。
⇒ **改完代码必须重新 build 镜像、重建容器**，否则你会对着"明明改了却没生效"怀疑人生。

**坑 B：`COPY . .` 把不该进去的也抄进去了。**
实测进容器看 `/app`，除了 `api.py`，还躺着一整个 **`.git`**（版本库）、`__pycache__`、以及
几个 `.md` 笔记 —— 这些跟"跑起来"毫无关系，却让镜像白白变大。
⇒ 正规做法是在项目里放一个 **`.dockerignore`**（跟 `.gitignore` 一个意思），把 `.git`、`__pycache__` 排除掉。

### 🔴 那么问题来了：为什么我在服务器上 `python api.py` 报"没有 fastapi"？

> 这一节是 **2026-10-05 学员真实踩到的**。他当时的推断是「**是因为之前的 docker 没完成吧**」——
> **正好相反**，而且实测数字很干净：

| 在哪跑 | 有 fastapi 吗 | 实测 |
|--------|:------------:|------|
| **宿主上**（你 SSH 进去的那个 Ubuntu） | ❌ **没有** | `python3 -c "import fastapi"` → `ModuleNotFoundError` |
| **容器里**（`fangji-api`） | ✅ **有，0.141.1** | `pydantic 2.13.4` · `uvicorn 0.52.0` |

**宿主上没有 fastapi，不是"Docker 没装完"，而是 Docker 干得对：**
依赖**故意**只装在镜像里 —— 这样宿主环境干干净净，你就算把宿主上的 Python 玩坏了，
容器里的服务照样跑。

**⇒ 记住这一条：依赖装在哪，你就得在哪跑。**

```bash
# ❌ 在宿主上跑 —— 没有 fastapi（而且见下面第二个原因，装了也不行）
python api.py

# ✅ 正确的启动命令（这是 uvicorn 的写法，不是 python 的）
uvicorn api:app --host 0.0.0.0 --port 8000
#        ↑    ↑
#        │    └─ 文件里那个叫 app 的对象（就是 @app.get(...) 里那个 app）
#        └────── 文件名，**不带 .py**
```

### 🔴 第二个原因：`python api.py` 就算装了 fastapi 也起不来

实测 `api.py` 里**没有** `if __name__ == "__main__":` 这一段（全文 700 多行，一行都没有）。

| 命令 | 它在问什么 | 结果 |
|------|-----------|------|
| `python api.py` | "把这个文件**当脚本从头执行一遍**" | 文件里只是**定义**了一个 `app` 对象，执行完就结束了 —— **不会起服务器** |
| `uvicorn api:app` | "去 `api` 这个文件里，找到叫 `app` 的对象，**拿它当服务器跑起来**" | ✅ 这才是启动 |

**所以你的报错是"两层"，只解决第一层还会卡在第二层。**
（`uvicorn api:app` 这个 `模块:对象` 的写法，你在本机跑 `我的练习/api.py` 时也用过 —— 是同一个东西。）

### 🔴 但最重要的第三件事：**你的服务现在就在跑，你不需要启动它**

实测（2026-10-05）：

```bash
curl -s -o /dev/null -w "%{http_code}\n" localhost:8009/docs
# 200   ← 它活着，而且已经活了 65 天
```

浏览器打开 **`http://123.58.220.17:8009/docs`** —— 那就是你的方剂 API 的接口文档页面，
能直接点开试每个接口。

⇒ **你要学的不是"怎么启动它"，是"怎么看出它在跑、怎么看它的日志、怎么重启它"** ——
那正是**任务 6 到任务 9**。你没有卡住，你只是**跳过顺序先动手了**（这本身是好事）。

### 你只需要会这 5 条命令（任务 8/9/10 会用到）

```bash

docker ps -a                 # 连"已经停了的"一起看

```

> ⚠️ **危险命令**（本页最上面那张表里也有）：`docker rm -f $(docker ps -q)` 会**删掉所有容器**。
> 先 `docker ps` 看清楚，再**指定名字**操作。**永远不要用 `-q` 那种"全都来一遍"的写法。**

### 任务 6 · 8009 端口被谁占了？

**目标**：查出监听 8009 的进程，拿到它的 **PID**。

**验证**：`sudo ss -tlnp | grep 8009` 的输出里有 `LISTEN`，**并且**有 `pid=数字`

> 🔴 **关键：不加 `sudo` 看不到 PID（2026-10-05 实测）**
> 你会看到两行 `LISTEN`，但 `users:(...)` 那一栏**是空的**。对比 8080 那行就有 `users:(("node",pid=1650,...))`。
> **原因**：占着 8009 的进程是 **root** 的，而 `ss -p` 只显示**你有权限看的**进程。
> **这不是你敲错了，是权限。** 这台机器的 sudo 是免密的，直接加 `sudo`。

**提示**：`ss` 是新一代的 `netstat`。

<details><summary>答案</summary>

```bash
# ① 不加 sudo —— 实测：两行 LISTEN，但【没有 pid】
ss -tlnp | grep 8009

# ② 加 sudo —— 实测：pid 出来了
sudo ss -tlnp | grep 8009
#   LISTEN ... 0.0.0.0:8009  users:(("docker-proxy",pid=1373923,fd=8))     ← IPv4
#   LISTEN ...    [::]:8009  users:(("docker-proxy",pid=1373941,fd=8))     ← IPv6

# 换个工具交叉验证（实测一致）
sudo lsof -i :8009
#   COMMAND     PID USER   FD   TYPE  ...  NAME
#   docker-pr 1373923 root    8u  IPv4  ...  TCP *:8009 (LISTEN)

# 老系统上可能是：
netstat -tlnp | grep 8009
```
**概念**：**PID = 进程编号**，是你在 Linux 里"指认"一个进程的唯一方式。
一个端口同一时刻只能被一个进程监听 —— 所以"端口被占用"的本质是"那个进程还没死"。

🔑 **但这里有个反直觉的结论，任务 7 马上要用到**：
占着 8009 的**不是你的 Python 服务**，而是 **`docker-proxy`** —— Docker 派到宿主上"接客"的传话员。
你的 `uvicorn` 真正跑在**容器里面**（宿主 8009 → 容器 8000）。
⇒ **你会拿到两个不同的 PID，别把它们当成同一个**（任务 7 教你怎么拿另一个）。
</details>

### 任务 7 · 这个进程是什么时候起的？跑了多久？

**目标**：看**你的服务**的**完整启动命令**和**已运行时长**。

> ⚠️ **别拿任务 6 那个 `docker-proxy` 的 PID 来查** —— 那查出来是"传话员"的信息，不是你的服务。
> 你的服务在容器里，**用进程名找它最省事**。

**验证**：能看到 `etime` 形如 `65-14:18:11`（65 天 14 小时…）

<details><summary>答案</summary>

```bash
# ① 按名字找（推荐）—— 实测一条命中
pgrep -af uvicorn
#   1373902 /usr/local/bin/python3.12 /usr/local/bin/uvicorn api:app --host 0.0.0.0 --port 8000
#   ↑PID     ↑解释器                ↑模块:应用   ↑监听地址:端口
#   （这个数字是 2026-10-05 的实测值，重启后会变 —— 别照抄）

# ② 拿①里那个 PID 查时长
ps -p <上一步的PID> -o pid,etime,cmd
#   实测输出：1373902  65-14:18:11  /usr/local/bin/python3.12 /usr/local/bin/uvicorn api:app ...
```
**概念**：`ps -o` 是"我要看哪几列" —— 列名可自选，比 `ps aux | grep` 干净得多。
**`etime` 很有用**：如果它显示只跑了几分钟，说明**进程刚重启过**，那问题可能刚发生。
</details>

### 任务 8 · 它是怎么被启动的？

**目标**：搞清楚你的服务是用 **systemd** 管的，还是 **docker** 跑的。

**验证**：`systemctl status xxx` 或 `docker ps` 能对上号

<details><summary>答案</summary>

```bash
# ① 先问 systemd：有没有这么一个服务？（实测：无）
systemctl list-units --type=service | grep -i -E "api|uvicorn|fastapi"
systemctl status <服务名>          # 看状态、最近日志、启动命令

# ② 再问 docker（实测：命中了）
docker ps
#   CONTAINER ID   IMAGE               PORTS                      NAMES
#   433770114fad   prescription-api    0.0.0.0:8009->8000/tcp     fangji-api     ← 就是它
docker logs --tail 50 fangji-api   # 看容器日志
docker port fangji-api             # 实测：8000/tcp -> 0.0.0.0:8009
```
**概念**：**知道"谁在管这个进程"才能正确地重启它。**
systemd 管的用 `systemctl restart`；docker 跑的用 `docker restart`。
**用错方式重启 = 起了一个野进程，然后端口冲突。**

🔑 **实测答案（2026-10-05）**：你的服务是 **docker 跑的**，容器名 **`fangji-api`**，镜像 `prescription-api`，
**没有**对应的 systemd 服务。所以任务 9 该用 `docker restart`，不是 `systemctl restart`。
（另外 `systemctl list-units` 那步**输出为空也要会读** —— "没找到"本身就是答案的一半。）
</details>

### 任务 9 · 正确地重启它

**目标**：把服务重启一次，**且做到"重启前后都没报错、服务真的起来了"**。

**验证**：重启后 `sudo ss -tlnp | grep 8009` 能看到**新的 PID**；`curl -s localhost:8009/docs -o /dev/null -w "%{http_code}"` 返回 **200**

> ⚠️ **验证命令要加 `sudo`** —— 理由和任务 6 一样（那两行 `LISTEN` 属于 root，不加 sudo 看不到 PID）。

**提示**：先确认是 systemd 还是 docker（任务 8）。

<details><summary>答案</summary>

```bash
# systemd
systemctl restart <服务名>
systemctl status <服务名> --no-pager | head -20

# docker（实测你的情况就是这个）
docker restart fangji-api
docker logs --tail 30 fangji-api

# 不管哪种，最后都验证一下（两件事都要做）
sudo ss -tlnp | grep 8009
#   实测：docker-proxy 的 PID 变了（1373923 → 新数字）= 容器真的重建了监听
curl -s -o /dev/null -w "%{http_code}\n" localhost:8009/docs
#   实测：200 —— 这才是"服务真的起来了"
```
**概念**：**"命令没报错" ≠ "服务起来了"** —— 必须用端口 + HTTP 状态码验证。
这跟你写代码要跑测试是同一个道理。

> 📌 **两个数字要一起看**：`docker-proxy` 的 PID **变了**（说明重启确实发生了），
> 而 `/docs` 返回 **200**（说明服务确实可用）。
> **只看其中一个都会被骗**：PID 没变 = 其实没重启成功；只看 200 = 可能是旧进程还在答。
</details>

### 任务 10 · 一次看清所有 python 进程

**目标**：列出所有 python 相关进程，数一下有几个。

**验证**：先出列表，再出一个数字

<details><summary>答案</summary>

# 微课 3 · 让它自己跑（预计 25 分钟）

**3 个新概念**：① 权限位（rwx / 644 / 755）② shebang 与可执行脚本 ③ cron 定时

### 任务 11 · 读懂 `-rwxr-xr-x` 这串东西

**目标**：随便找个文件，说出它的权限是什么意思、谁能读谁能写谁能执行。

**验证**：`stat -c "%a %n" 文件名` 输出的数字，和 `ls -l` 的字母能对上

<details><summary>答案</summary>

```bash
ls -l script.sh
# -rwxr-xr-x  1 root root  123 ... script.sh
#  ↑↑↑↑↑↑↑↑↑
#  第1位：- 普通文件 / d 目录 / l 链接
#  后 9 位每 3 个一组：所有者(u) / 同组(g) / 其他人(o)
#  r=4  w=2  x=1

stat -c "%a %n" script.sh      # 755
```
**记忆法**：`755` = `rwxr-xr-x`（4+2+1 / 4+1 / 4+1）；
`644` = `rw-r--r--`（配置文件常见，**谁都不能执行**）。

**⚠️ 不要用 `chmod -R 777`** —— 那是"所有人都能改"，等于把门拆了。
</details>

### 任务 12 · 写第一个脚本

**目标**：写一个脚本：**数出日志里的 ERROR 行数，超过 10 就打印告警**。

**验证**：手工往日志里塞 11 行 ERROR，跑脚本，应该看到告警

<details><summary>答案</summary>

```bash
#!/bin/bash
# check_errors.sh —— 数 ERROR 行，超过 10 告警
LOG=/var/log/app.log
LIMIT=10

COUNT=$(grep -c ERROR "$LOG")
echo "ERROR 行数：$COUNT"

if [ "$COUNT" -gt "$LIMIT" ]; then
    echo "⚠️ 告警：ERROR 超过 $LIMIT 条！"
fi
```
**概念**：① 第一行 `#!/bin/bash` 叫 **shebang**，告诉系统用哪个解释器跑它
② `$(命令)` 是**命令替换** —— 把命令的输出当成值赋给变量（等价于你 Python 里的函数调用取值）
③ `[ "$COUNT" -gt "$LIMIT" ]` 的数字比较用 `-gt`，**不是 `>`**（`>` 在 shell 里是重定向！这是个经典坑）
</details>

### 任务 13 · 让它能被执行

**目标**：把任务 12 的脚本变成可以直接 `./check_errors.sh` 跑。

**验证**：`./check_errors.sh` 能跑出结果，而不是报 `Permission denied`

<details><summary>答案</summary>

```bash
chmod +x check_errors.sh     # 只给"执行"权限，别用 777
./check_errors.sh            # ./ 表示"当前目录下的这个文件"

# 如果报 "bad interpreter"，是 shebang 那行写错了或文件有 Windows 换行符
# 修：sed -i 's/\r$//' check_errors.sh
```
**概念**：Linux **不会执行没有 x 权限的文件**，哪怕它是脚本。
**为什么必须写 `./`**：当前目录默认不在 `PATH` 里 —— 这是**安全设计**，
防止你 `cd` 到别人目录里，敲个 `ls` 却跑了他放的恶意脚本。
</details>

### 任务 14 · 让它每 5 分钟自己跑一次

**目标**：用 cron 定时执行任务 12 的脚本，并把结果追加到文件。

**验证**：`crontab -l` 能看到你加的那行；等 10 分钟看输出文件有没有变长

<details><summary>答案</summary>

```bash
crontab -e        # 打开编辑器，加一行：
*/5 * * * * /root/check_errors.sh >> /root/check_errors.out 2>&1

crontab -l        # 确认加上了
```
**概念**：`*/5 * * * *` 五个字段 = **分 时 日 月 周**：
`*/5` 每 5 分钟 ｜ `0 3 * * *` 每天 3 点 ｜ `0 3 * * 1` 每周一 3 点。

**两个必踩的坑**：
- **`2>&1` 不能省** —— cron 的错误默认发邮件，不写这个你什么都看不到
- **cron 的环境变量和你登录时不一样**，脚本里**尽量用绝对路径**
</details>

### 任务 15 · SSH 免密登录

**目标**：配好从本机到服务器的免密登录（不用每次输密码）。

**验证**：`ssh ubuntu@123.58.220.17` 直接进去，不问密码

<details><summary>答案</summary>

```bash
# 1) 本机生成密钥（已有就跳过）
ssh-keygen -t ed25519 -C "我的电脑"

# 2) 把公钥传上去（这一步还会问一次密码）
ssh-copy-id ubuntu@123.58.220.17

# 3) 验证
ssh ubuntu@123.58.220.17 "hostname; uptime"
```
**概念**：`~/.ssh/id_ed25519` 是**私钥，绝不外传**；
`id_ed25519.pub` 是**公钥，就是要给服务器的**。
服务器把它追加到 `~/.ssh/authorized_keys` 里 —— `ssh-copy-id` 就是替你干这件事。

> ⚠️ **用户名是 `ubuntu` 不是 `root`** —— 公钥要传到 `/home/ubuntu/.ssh/authorized_keys`。
> 传到 `/root/.ssh/` 的话，用 `ubuntu` 登录时**照样要密码**（免密是"用户级"的，不是"机器级"的）。
</details>
