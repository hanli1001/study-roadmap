① 三种表的分工（关系模型）

表的角色装什么
人表 / 群表各自独有的信息（姓名、群名、手机号）
绳子表（关联表）只记"谁连着谁"：两列 id + 属于这段关系的信息（如加入时间、用量、身份）
三步推导法（遇到新需求就这么推）
① 数一数有几种"东西" → 每样一张表
② 每个事实跟着谁走？只跟一个 → 放它自己的表
③ 跟两个走的（如"谁在哪个群"）→ 单独做绳子表
为什么不能省掉第三张表
· 塞进人表 → 一个人加 10 个群就要存 10 行
· 塞进群表 → 200 人的群，群名要重复 200 遍
· 用 id 而不是名字做绳子 → 名字改了不用全库改

② JOIN 模板（照抄改表名）

SELECT 要看的列
FROM 主表
JOIN 绳子表 ON 主表.id = 绳子表.主表_id
JOIN 另一张表 ON 绳子表.另一张_id = 另一张表.id
WHERE 筛选条件;
字段作用
ON配对规则：拿哪个 id 去对哪个 id（接反了就全错）
WHERE筛选：配对完之后，只要哪几行
JOIN两边都配上才出行
LEFT JOIN左表一行都不丢，右边配不上填 NULL

③ 执行过程（背这 4 步）

  • ① 从主表拿出一行（如 id=1 的群）
  • ② 拿这个 id 去绳子表一行行比
  • ③ 每条配上的行，拿另一个 id 去目标表换出名字
  • ④ 拼成一行交出去
结果行数 = 配对成功的次数，不是任何一张表的行数。

④ 查出来不对时的排查（三步）

#做什么
1单独数绳子表：SELECT * FROM 绳子表 WHERE ...; 看应有几行
2再数 JOIN 的结果行数
3两数一致 ≠ 配对正确 → 挑一行人工核对内容
JOIN 的两种"错法"（实测过）
· id 空间不重叠 → 0 行，不报错（空的，还看得出来）
· id 空间重叠 → 照样出数据，看着还挺合理（静默错误，最危险）
👉 所以"不为空"绝不等于"对"

⑤ 常见报错/症状

症状多半是
结果 0 行但不报错ON 接反 / 条件写错
行数比预期多很多配错了、或多对多没经过绳子表
某一列全是 NULL用了 LEFT JOIN 且右边没配上（正常）
no such column列名写错 / 忘了用表别名
ambiguous column两张表都有这列名 → 前面加表名

⑥ 别忘的老三样

  • ? 占位符防注入，永远别 f-string 拼 SQL
  • 增删改之后必须 conn.commit()（≈ git commit）
  • 用完 conn.close()（托盘放回）
