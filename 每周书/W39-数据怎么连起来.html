三步推导法：第三张表是被「逼」出来的

本课第一个新概念：第三张表不是"数据表"，是"绳子表"。

这一章的回答对象是 P-009：JOIN 关系表一直不理解。但你的 sql-notes.md（7 月自己写的）里， 多对多、关联表、JOIN、执行过程四节全都在 —— 所以断点不在语法，在为什么非要有第三张表。

① 三个业务事实

  1. 一个人 → 一个手机号（一个格子就够）
  2. 一个群 → 一个群名（一个格子就够）

第 3 章

一行行带着 id 去问名字：JOIN 到底做了什么

本课第二个新概念：执行过程。看懂这一章，JOIN 就不再是咒语。

要查的东西：1 号群的成员名字。可绳子表里只有数字，名字在另一张表 —— 于是：

SELECT persons.name, groups.name
FROM groups
JOIN group_members ON groups.id = group_members.gid
JOIN persons       ON group_members.uid = persons.id
WHERE groups.id = 1;

逐行问自己：

FROM groups —— 先站哪张表？（主干：我要 1 号群）
第 1 行 ON —— 拿什么去配什么？（groups.id = group_members.gid）
第 2 行 ON —— 绳子拿到了 uid，去哪换名字？（persons 表）
WHERE groups.id = 1 —— 为什么这条写在最后、长得还不一样？（它才是筛选 —— 第 4 章）

数据库实际做的四步

步数据库在干什么数据长什么样
1从 groups 拿出 1 行1 | 高数自习
2拿着 1 去 group_members.gid 一行行比命中 (7,1) ✓ (9,1) ✓ (7,2) ✗
3每条命中的行，拿 uid 去 persons.id 换名字7→小明、9→小红
4拼成行交出去小明 | 高数自习、小红 | 高数自习

🔑 结果 2 行，不是因为"1 号群有 2 个人"，而是因为"配对成功了 2 次"。 这两句话平时结论一样，但换一张表就不一样了 —— 这是本书第 5 章要用的伏笔。

立即复刻（别往下看，先自己写）

-- 把「1 号群的成员名字」改成「2 号群」
SELECT persons.name FROM ??? JOIN ??? ON ???  WHERE ???;

答案在你自己手上：只改 WHERE 那一句就够了（groups.id = 2）—— 因为 JOIN 说的是"怎么配"，WHERE 说的是"要哪个"。配法没变，只有筛选变了。

第 4 章

ON 和 WHERE：配对 ≠ 筛选

本课第三个新概念。也是最容易"看起来懂了"的一个。

关键字管什么一句话
ON怎么配（横着拼）决定两张表的行怎么对上 —— 配不上的行直接消失（INNER JOIN）
WHERE要哪些（竖着筛）配对完成之后，把不要的行筛掉

顺序为什么是这样

FROM  →  JOIN … ON  →  WHERE  →  GROUP BY  →  HAVING  →  SELECT  →  ORDER BY  →  LIMIT

真实执行顺序里，WHERE 排在 ON 后面、GROUP BY 前面。 所以：WHERE 里看不见聚合函数（第 7 章会撞上这个报错）； 而 ON 里写的条件，是在"配"的当下生效的。

⚠️ 一个真实差别：LEFT JOIN 时，把条件写在 ON 里和写在 WHERE 里 结果完全不同 —— 写在 WHERE 里会把"右表配不上、整行是 NULL"的那些行筛掉， 于是 LEFT JOIN 白写了，退化成 INNER JOIN。这是统计时最常踩的坑。

合上书，你要能回答：
  1. ON 和 WHERE 各管什么？一句话。
  2. 哪一句执行得更早？
  3. LEFT JOIN 里把条件塞进 WHERE，会发生什么？
第 5 章

JOIN 什么时候在骗你

这一章是本课最实用的一章 —— 因为它讲的是"不报错的错"。

ON 写错的后果不是一种，是两种，而且都不报错：

情况实测结果危险度
id 空间不重叠
（人 7/9、群 1/2）		错配 → 0 行低：空的，一眼看得出来
id 空间重叠
（两套都从 1 开始编号）		错配 → 照样出数据，看着还挺合理🔴 高：静默错误

你自己的库里就有这个雷（实测）

prescriptions.db 里 prescriptions.id 与 ingredients.id 都从 1 开始。 把配对准写成 p.id = pi.ingredient_id 之后，查询返回了 20 行（麻黄汤配麻黄……）， 看着像对、其实全错，而且不报错。

今天新测的一个更狠的例子

用「学生 / 课程 / 选课」三张表，把 ON 的两头接反：

✅ 正确写法

student | course | grade --------+----------+------ 韩立 | 数据库 | 88.5 韩立 | 高数 | 76.0 小明 | 数据库 | 92.0 小明 | 机器学习 | 81.0 小红 | 英语 | 59.0 小刚 | 体育 | NULL （6 行）

❌ 两头接反

student | course --------+--------- 韩立 | 数据库 小明 | 数据库 韩立 | 高数 小红 | 高数 小美 | 机器学习 小刚 | 体育 （6 行）

两张表都是 6 行。用 SQL 自己对了一遍：正确结果里有 2 行在错误结果里找不到， 错误结果里凭空多了 2 行。
而且破绽其实很扎眼：小美根本没选过课，却出现在了选课表里。 ⇒ 只数行数永远发现不了，必须看内容。

诊断三步（本课最该带走的东西）

  1. 单独数绳子表：SELECT * FROM prescription_ingredients; —— 实测 49 行
  2. 再数 JOIN 的结果行数 —— 也是 49 行
  3. 🔴 两个数一致 ≠ 配对正确 —— 还要挑一行人工核对内容
  4. 数字明显对不上（空 / 多很多）→ 几乎一定是 ON 写错

👉 所以 JOIN 查出来是空的时候：先怀疑 ON，别怀疑"数据没了"。 而 JOIN 查出来不为空的时候：也别急着高兴，核对一行内容再说。

  1. ON 接反的两种后果各是什么？哪种更危险？
  2. 「两数一致」为什么不等于「配对正确」？

第 6 章

搬回你自己的库：换皮三跳

下面用的就是你 7 月自己建的 prescriptions.db —— 结构一模一样，只是绳子换了名字。

这就是迁移，不是"新东西"：

微信群例你的方剂库
persons（人）ingredients（药材）
groups（群）prescriptions（方剂）
group_members（谁在哪个群）prescription_ingredients（哪方有哪药）
joined（加入时间）dosage（用量）

换皮 1（L1 复刻 · 照抄改名）

SELECT p.name, i.name, pi.dosage
FROM prescriptions p
JOIN prescription_ingredients pi ON p.id = pi.prescription_id
JOIN ingredients i ON pi.ingredient_id = i.id;

跑之前先猜：会出多少行？—— 实测 49 行，因为关联表里正好 49 条绳子。

换皮 2（L2 变式 · 反着查）

「甘草出现在哪些方剂里？」—— 起点要换成哪张表？

SELECT p.name, pi.dosage
FROM ingredients i
JOIN prescription_ingredients pi ON i.id = pi.ingredient_id
JOIN prescriptions p ON pi.prescription_id = p.id
WHERE i.name = '甘草';

注意：起点换了，两句 ON 也跟着换 —— 但配对关系没变（还是那两根绳子）， 只是"从哪头出发"变了。这就是"变式"的意思。

换皮 3（L2 变式 · 统计）

SELECT p.name, COUNT(pi.ingredient_id)
FROM prescriptions p
LEFT JOIN prescription_ingredients pi ON p.id = pi.prescription_id
GROUP BY p.id;

只讲一句：LEFT JOIN = "左边的表一首都不能丢，配不上的填 NULL"。 点破：如果把 LEFT 去掉，药材数 0 的方剂会整行消失 —— 这是统计时最常见的坑。

为什么先给你看：上课时你会有"原来是这样"的位置。但别在这里深挖 —— 提前把细节嚼一遍，上课就不新鲜了（生成效应会打折）。

① 分组统计：GROUP BY + 聚合函数

要回答的问题是：「每个群各有几个成员？」—— 一行一行出结果不行，得"分堆"。

SELECT cid, COUNT(*) AS n
FROM enrollments
GROUP BY cid
ORDER BY n DESC;

要点三句：

  • COUNT(*) 数行；COUNT(列) 只数这一列不是 NULL 的行 —— 两者不一样就说明有 NULL。
  • SELECT 里只能出现分组列 + 聚合函数。写了别的列 SQLite 不报错，会随便挑一行给你（别的数据库直接报错）。
  • 要筛"哪几堆"，用 HAVING；写成 WHERE COUNT(*) > 1 会报 misuse of aggregate —— 因为 WHERE 执行时还没分组。

② 那个会骗人的 NULL：= NULL 永远查不出东西

SELECT sid, cid FROM enrollments WHERE grade = NULL;      -- 实测：0 行（而且不报错）
SELECT sid, cid FROM enrollments WHERE grade IS NULL;     -- 实测：1 行 ✅

NULL 的意思是"不知道"，所以"等不等于不知道"的答案是"我也不知道"。 同理 WHERE grade <> 80 也不会把 NULL 的行选出来。

上课前，你只要能做到：
  1. 说出「分组统计要解决的问题是什么」（不是怎么写）。
  2. 看到 misuse of aggregate function 这个报错，知道该往哪个方向查。
  3. 记住 = NULL 是错的，正确的是 IS NULL。

找错ON groups.id = group_members.uid 错在哪？群 id 对人 id，两头接反 → ① 不重叠时 0 行、不报错 ② 重叠时返回"看着合理"的假数据，同样不报错
方法JOIN 结果为空，你先怀疑什么？不为空呢？为空 → 怀疑 ON；不为空 → 也要核对一行内容
