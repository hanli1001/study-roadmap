① 把两条外键加回去 · 5 分钟 · 这是唯一还没做的改动

第一轮我说的是「重写三条外键：只留指向两张主表 id 的两条，父表名写对」—— 你把它们整段删掉了。这两种做法不一样：

  • 写对 = 数据库帮你拦"id 写错" → 这正是第一轮让你吃亏的那类 bug
  • 删掉 = 这张绳子表现在一条约束都没有（除了主键）→ 下次 id 写错，照样静默进去
实测 —— 探针 1：你现在的 D8.db外键声明（PRAGMA foreign_key_list）： 【一条都没有】 外键开关（PRAGMA foreign_keys） ： 0 （0 = 关） 实测 —— 探针 4：把它加回去之后呢？ 加约束后跑出来的最后一行： [('数学','张三','高一'), ('数学','李四','高三'), ('数学','牛二','高三'), ('数学','李三','高一'), ('数学','张贾瑞','高二')] => 跟你现在的结果一模一样 ⇒ 加约束不用改你任何数据 外键开着时：插 course_id=1（存在） -> 成功 外键开着时：插 course_id=99（不存在）-> IntegrityError -> FOREIGN KEY constraint failed

说人话：加这两行 + 一行 pragma，你现在的脚本一个字都不用改，输出完全一样—— 但从此以后 id 写错会当场报错，而不是等到 JOIN 出来少了行才发现。 纯赚，不亏。具体怎么写，函数卡搜「外键」（sql.foreign_key）那张就是。

顺手发现一个雷：WHERE c.name = "数学"

第 77 行，字符串用了双引号。现在能跑，但这是碰巧能跑 —— SQLite 里 "..." 优先当列名解析，只有在找不到同名列时才退化成字符串（历史兼容行为）。实测：

实测 —— 探针 3A) 表里没有叫 数学 的列 —— 现在能跑： [(1, '数学')] B) 只要有人加了一列真的叫 数学 —— 同一条 SQL： [] ← 变成空结果，而且不报错 原因：SQLite 优先把 "..." 当列名；找不到同名列才退化成字符串 正确：单引号 [(1, '数学', 0)] 更好：占位符 [(1, '数学', 0)]

你不会收到任何报错，只会收到一个空列表 —— 然后开始怀疑数据、怀疑 JOIN、怀疑人生。 这类"不报错的错"第一轮已经咬过你一次（那次是列名和值写反）。

改法：WHERE c.name = '数学'（单引号），或者干脆 WHERE c.name = ? 配 ("数学",) —— 占位符最好，因为它连"引号该用哪个"这个问题都取消了（你第一轮的第 44 行就是栽在参数上）。
