💡 这就是"检索"这一层要解决的核心问题，也是 RAG 里 R（Retrieval）存在的理由 —— 不是"把文档喂给模型"那么简单。

② 三档做法（从你现在的位置出发，一级一级升）

档位怎么做复杂度缺陷
① 逐条扫描
（你现在）		每个问题，把 N 条内容全看一遍，看关键词在不在O(N) 每次数据一大就慢；只会字面匹配（见①）
② 倒排索引
（关键词检索）		事先建"词 → 出现在哪几条"的表；查词直接跳过去建表一次，查询 O(1)~O(词频)仍然只认字面：同义词、近义词、换个说法就查不到
③ 向量检索
（语义检索）		把每条内容和问题都变成一个"意思坐标"（向量），找距离最近的要算向量（有成本），查询快要模型/embedding 服务；结果需要评估（可能"像但不对"）
💡 真实系统常常混着用：关键词（②）保准 + 向量（③）保语义 → 这就是 hybrid search。第 3 档不是取代前两档，而是补盲区。

用户提问→也算成向量→检索 top-k→ 拼进提示词→大模型生成回答→附上引用来源

⑤ 一个必须建立的心智模型：模型只看到你塞给它的东西

大模型自己不知道你的方剂库。它回答得好不好，取决于你从库里检索了哪几段塞给它。
检索给什么模型只能据此回答
检索到"四君子汤 · 脾胃气虚…"围绕这条回答，可引用来源 ✅
检索到 0 条（字面匹配的盲区）要么说"没有相关信息"，要么开始编（幻觉）
检索到一大堆不相关的答案被带偏；还浪费 token
👉 所以 RAG 的功夫八成在检索质量上，不在"换个更强的模型"。
这也是为什么下一步要学怎么量检索好不好（召回率：该找到的找到了吗；准确率：找到的对不对）。

⑥ 你先自己写

任务①：用 SQL 写一个"倒排索引"的雏形 —— 建一张表记录"每个症状词出现在哪些方剂里"（提示：先拆词/或用 LIKE 反向统计）。
任务②：用 Python 算两个句子的"字面相似度"（共有词数 / 总词数），观察"免疫"和"气虚"算出来是几分 —— 体会为什么字面相似度不够用。
# 任务②的骨架
def literal_similarity(a, b):
    """返回 0~1：两个字符串共有多少字（最粗的相似度）"""
    sa, sb = set(a), set(b)
    return len(sa & sb) / len(sa | sb)   # 交并比

print(literal_similarity("气虚", "免疫"))     # 先猜，再看结果
print(literal_similarity("气虚", "气虚"))
跑完你会得到一个"0"—— 这就是向量检索存在的理由：意思相近的两个词，字面相似度是 0。
