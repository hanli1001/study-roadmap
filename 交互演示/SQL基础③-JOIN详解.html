① 为什么需要 JOIN：从"一张表放不下"说起

假设把"谁在哪个群"硬塞进人表：

persons
id | name | 群1     | 群2     | 群3   ← 一个人最多加 3 个群？
7  | 小明 | 高数自习 | 游戏开黑 | (空)  ← 第 4 个群往哪写？
问题① 列数不够：群的总数是不固定的，表结构不能天天改
问题② 大量空白：加 1 个群、99 个空列
问题③ 改不动：把"高数自习"改名 → 表里 N 行都要改
✅ 正确做法：拆成两张表 + 中间一张"绳子表"，查的时候再用 JOIN 拼回来
💡 一句话：存储时拆开（避免重复），查询时拼回（JOIN） —— 这就是关系型数据库的核心思路。

④ 四种连接：留下谁、丢掉谁



  

    
类型一句话行数规则

    
INNER JOIN（JOIN）只留两边都配上的= 配对成功的次数

    
LEFT JOIN左表一行都不丢，右边配不上填 NULL≥ INNER 的行数（多了那些"没配上的左行"）

    
RIGHT JOIN右表一行都不丢（SQLite 老版本不支持，可用左右对调代替）对称于 LEFT

    
FULL OUTER JOIN两边都不丢（SQLite 不支持，要 UNION 模拟）最多

    
CROSS JOIN不要 ON，每行两两组合（笛卡尔积）= 左行数 × 右行数

  

  
判断口诀：问"哪边的数据一行都不能少？" → 是左边就 LEFT JOIN，两边都要就 FULL。

  
忘了写 ON 会变成笛卡尔积：3 行 × 4 行 = 12 行 —— 结果突然暴增，多半是 ON 写漏了。

  
💡 你最常用的是前两个：INNER（要匹配）和 LEFT（保留左边全部）。






⑤ ON vs WHERE：LEFT JOIN 里它们不一样（高阶坑）



  

    
ONWHERE

    
作用配对规则：怎么把两边的行接起来筛选：拼完之后再挑

    
执行时机拼接时拼接之后

    
INNER JOIN 里写哪边结果一样（所以很多人不知道区别）

    
LEFT JOIN 里写在 ON：配不上照样保留左行（右边 NULL）写在 WHERE：把右边为 NULL 的行筛掉了 → LEFT JOIN 白做，退化成 INNER

  

  
经典坑：LEFT JOIN b ON a.id=b.aid WHERE b.status='ok'

    → 那些"没有对应 b 记录"的行，b.status 是 NULL，不满足 ='ok' → 被删掉。

    想保留它们就把条件挪到 ON 里：LEFT JOIN b ON a.id=b.aid AND b.status='ok'






⑥ NULL 在 JOIN 里代表什么



  

    
你看到的含义

    
结果里某列是 NULL"右边没配上" —— 不是数据丢了，是本来就没有

    
LEFT JOIN 后 COUNT(右表.列)只数配上的（NULL 不计）；COUNT(*) 会把没配上的也算一行

    
用 WHERE 右表.列 = 'x'NULL 不满足任何比较 → 没配上的行消失（见⑤）

  

  
💡 想"只看没配上的"（找孤儿数据）：WHERE 右表.id IS NULL。






⑦ 查出来不对时的三步核对（实测过的两种错法）



  
① 单独数绳子表：SELECT * FROM group_members WHERE gid=1; → 应有几行

  
② 再数 JOIN 的结果行数 → 对比

  
③ 一致 ≠ 正确！还要挑一行人工核对内容

  

    
错法实测结果

    
id 空间不重叠（人 7/9、群 1/2）0 行，不报错 —— 空的，还看得出来

    
id 空间重叠（两套都从 1 开始，如方剂库）照样出数据，看着还挺合理 —— 静默错误，最危险

  

  
实测反例：prescriptions.id 与 ingredients.id 都从 1 开始。

    把配对准写成 p.id = pi.ingredient_id → 返回 20 行（麻黄汤配麻黄…），看着像对、其实全错，且不报错。

  
👉 结论："不为空"绝不等于"对"。JOIN 要核对的是配对，不是语法。






⑧ 换到你的真实库




-- 每首方剂有哪些药材（实测 49 行 = 绳子表行数）
SELECT p.name, i.name, pi.dosage
FROM prescriptions p
JOIN prescription_ingredients pi ON p.id = pi.prescription_id
JOIN ingredients i ON pi.ingredient_id = i.id;

-- 反着查：甘草（实测 7 首）—— 起点换成 ingredients
SELECT p.name FROM ingredients i
JOIN prescription_ingredients pi ON i.id = pi.ingredient_id
JOIN prescriptions p ON pi.prescription_id = p.id
WHERE i.name = '甘草';
